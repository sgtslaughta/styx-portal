## C. New issue (selkies): prefer a codec the viewer decodes in hardware

**Title:** Initial encoder choice ignores whether the *client* decodes it in hardware

> **What happens.** `nextRung` (selkies-ws-core.js) orders encoders by `HARDWARE_ORDER`
> among those the **server** encodes in hardware (`encoderBackends[codec].hardware`),
> then takes the first the client can decode at all (`canDecodeEncoder`) — software
> decode counts. The client already asks whether it has a **hardware** decoder
> (`pageDecode.hardware`, via `isConfigSupported({hardwareAcceleration:
> 'prefer-hardware'})`), but only the stats panel uses the answer.
>
> **Effect, measured.** Server: Radeon 780M, VA-API AV1 + HEVC + H.264. Client: Windows
> Chrome 156 on an RX 6500 (Navi 24: no AV1 decode block; HEVC/H.264/VP9 in hardware).
> AV1 was chosen and decoded in software: panel "decoder: Software · No hardware decoder
> for this stream", decode 1.96 ms/frame. Forcing HEVC first on the server: "decoder:
> Hardware · NV12 frames · H.265", decode 0.74 ms, arrival-to-screen 0.92 ms. At
> 2560×1440 and 120 Hz (this client's monitors) software AV1 is where stutter starts.
> Same effect over WebRTC with HEVC: `D3D11VideoDecoder`, `powerEfficientDecoder=true`.
>
> **Proposal.** When picking the initial encoder (and in `nextRung`), rank server-hardware
> codecs by whether this client decodes them in hardware first, then efficiency:
> `[...hw_encode ∩ hw_decode by HARDWARE_ORDER, ...hw_encode ∩ sw_decode, ...rest]`.
> Probe once per codec at connect (1280×720 is enough; `isConfigSupported` with
> `prefer-hardware`, same timeout as the existing probe), cache per page like the
> existing decoder probe. Keep a user pick authoritative; this only changes the default.
> For WebRTC the equivalent is `RTCRtpReceiver.getCapabilities('video')` plus a
> `MediaCapabilities.decodingInfo({type:'webrtc', …}).powerEfficient` check.
>
> Happy to send a PR with tests (Playwright fake-decoder probe) if the direction is OK.

## D. New issue (selkies): automatic WebSockets fallback when WebRTC media can't flow

**Title:** Dual mode: fall back to WebSockets automatically (and remember it) when the
WebRTC media path fails

> **Context.** Main already detects a failing media path beside a working signaling
> socket (`transportAdvice` → toast with "Switch to WebSockets" when dual mode is on).
> The user still has to notice and click, and the next visit from the same network
> fails the same way.
>
> **Measured case.** Corporate network, client with a public IP behind a firewall that
> passes outbound UDP to STUN but drops unsolicited replies from other peers. Server
> behind a home NAT with endpoint-independent, port-preserving mapping (one socket →
> same mapped port to three STUN servers). Without TURN: local `srflx` gathered, all
> 16 pairs stuck `in-progress`, no media. With Cloudflare TURN
> (`enable_cloudflare_turn`): selected pair = local `relay` (udp) ⇄ server `srflx`,
> HEVC in hardware — works. So "UDP works to STUN" is not "P2P works", and the only
> reliable signal is the ICE outcome.
>
> **Proposal (opt-in, e.g. `webrtc_auto_fallback`, default off):**
> 1. On `transportAdvice` (or ICE `failed`, or no `succeeded` pair within N s,
>    default 8), with dual mode on and not a viewer, call `switchStreamMode('websockets')`
>    automatically and show a dismissible note instead of the blocking toast.
> 2. Remember the outcome per network for a day (localStorage key from the client's
>    reflexive address or the server-seen client IP), so the next connect starts on
>    WebSockets directly; a "Try WebRTC again" action clears it.
> 3. Optional policy `webrtc_relay_tcp_ok` (default true): when the only working pair
>    is a TCP/TLS relay, operators who pay per GB or care about head-of-line blocking
>    may prefer WebSockets; let them say so.
>
> Happy to prototype 1–2 against main.

## E. New issue (selkies): server-side idle timeout that covers WebRTC

**Title:** Idle timeout in the server, so it applies to WebRTC (data channel) input too

> Over WebSockets a reverse proxy can see input frames and enforce an idle timeout;
> over WebRTC input rides the data channel, invisible to anything but selkies itself.
> With a paid TURN relay (Cloudflare bills per GB of egress), a forgotten tab keeps
> relaying video indefinitely. Proposal: `idle_timeout` (seconds, 0 = off) and
> `idle_warn_lead`, measured in the server from the last *input* message on either
> transport (not acks/stats/pings); at lead time send the page a warning message, at
> timeout close the session (peer connection + data channels) with a reason the
> dashboard shows ("Disconnected after N min idle — Reconnect"). Optional
> `max_session` hard cap. We currently approximate this downstream with an injected
> activity beacon; doing it in the server would be authoritative and simpler for
> everyone.
